副标题
真正的问题是： Minecraft 究竟哪些部分天然适合并行， 哪些部分永远不应该并行。
本书目标
本书不试图直接回答：「Minecraft为什么不能多线程？」而试图回答：「Minecraft中的哪些系统满足： 快照化（Snapshot） 纯计算（Pure Compute） 无副作用（No Side Effects） 增量传播（Incremental） 事务化（Transaction） 状态所有权（Ownership）」以及：「这些条件是否足以建立： 下一代AE2 下一代科技模组 下一代Minecraft Runtime」
研究原则
本书遵循以下原则：
Principle-001
不要先设计线程。 而要先发现：「哪些计算值得被线程化。」
Principle-002
不要先相信优化。 而要先建立：「Profiler Replay Benchmark」体系。
Principle-003
不要把假说写成事实。 区分：「已证实结论 强假说 弱假说 失败路线」
Principle-004
讨论记录属于研究资料。 所有重要讨论：「提出 质疑 反例 修正 收敛」均应被记录。

开篇问题
本书起源于一个简单问题：「Minecraft为什么这么难多线程？」最初答案似乎非常简单：「加线程池。」随后问题变成：「不会加锁加到爆？」之后变成：「能不能VM化？」再后来变成：「哪些BlockEntity满足快照条件？」最终变成：「什么样的系统天然适合并行？」这也是本书真正的研究起点。

Chapter 1
JIT 幻想时代
起源问题
研究最初并不是从：「Minecraft Runtime」开始。 而是从一个更简单的问题开始：「AE2为什么慢？」随后扩展成：「Minecraft为什么不能利用多核？」
最初出现的思路可以概括为：
Tick
↓
VM
↓
伪字节码
↓
JIT
↓
缓存结果
↓
加速
此时产生了第一个核心设想：
Hypothesis-001
设想如下：「原始逻辑 for (10000) { read() save() }」转换为：「NEW_BATCH_TASK PUSH READ COUNT 10000 PUSH SAVE COUNT 10000 CALL THREAD」
目标： 不再让CPU理解：「for」而是直接理解：「任务」
产生了一个新的问题：「如果任务可以描述 是否可以缓存？」
于是出现：
Hypothesis-002
「高频任务 是否可以JIT命中？」例如：「运行10000次」直接变成：「返回缓存结果」
当时隐含前提是：「同样输入 得到同样输出」
第一轮质疑
很快出现反例。 例如：
if (gametick % 20 == 0)
{
    doSomething();
}
或者：
SavedData.read()
或者：
Random.nextInt()
这时出现第一个重要发现。
Discovery-001
Minecraft 大部分逻辑不是：「数学函数」而是：「状态机」
数学函数：
输入
↓
计算
↓
输出
Minecraft：「世界状态 实体状态 红石状态 玩家行为 随机数 时间」共同决定结果。
因此：「相同代码 可能得到不同结果」
于是：
Failed Route-001
「缓存READ结果」基本被判定为：「不能作为通用优化方案」
第一次转向
JIT路线没有完全被否定。 但发生了重要收缩。
原来目标：「优化所有逻辑」
变成：「寻找满足条件的逻辑」
这里诞生一个后来影响全书的思想。
Rule-001
不要问：「如何优化Minecraft？」先问：「什么东西值得被优化？」
研究重点第一次从：「优化器」变成：「目标识别」
第二轮讨论
此时开始讨论：「多线程」
出现一个经典问题：「不会加锁加到爆？」
因为：「线程A」可能访问：「World」
「线程B」也访问：「World」
于是：「锁竞争」会越来越严重。
这时提出一种激进思路：
Hypothesis-003
建立：「交互线程」
负责：「世界修改 实体修改 NBT修改 存档写入」
其余线程：「只计算」
形成：
Compute Thread

↓

Interaction Thread
模式。
这是整套研究路线里第一次出现：「状态隔离」思想。
虽然此时还没有提出：「Snapshot」概念。
但已经出现：「不要共享状态」的想法。
第一次重要收敛
此时讨论出现分叉。
路线A：「优化JIT」
路线B：「优化线程模型」
后来的研究证明：「路线B更重要」
于是得到：
ADR-001
JIT 可能有价值。 但：「状态隔离 远比JIT重要。」
章节结论
JIT幻想时代最大的贡献不是：「JIT」本身。
而是暴露了一件事：「Minecraft不是程序执行问题。 而是状态管理问题。」
本章最终结论
「JIT 不是第一研究对象。 状态 才是第一研究对象。」
引向下一章
当研究对象从：「代码」变成：「状态」之后。 下一个问题自然产生了：「什么样的状态 能够安全移动到主线程之外？」

Chapter 2
AE2-VM 与纯函数样本的发现
新问题
在 JIT 路线被削弱之后。 研究方向发生了变化。 问题不再是：「如何优化所有计算？」而变成：「什么样的计算 天然适合被优化？」
这看起来只是措辞改变。 实际上却意味着：「系统视角 取代 优化器视角」开始成为主流。
第一次重要观察
随着对 AE2 合成系统的研究。 出现了一个非常特殊的现象。
AE2 自动合成规划过程：「Pattern Library Inventory Request」输入固定。
输出：「Craft Plan」
并且：「生成计划期间 不会修改真实世界。」
不会：「setBlock spawnEntity saveNBT modifyChunk」
甚至：「库存变化」也不是在真实库存上完成。
而是在：「模拟库存」上完成。
这一点极其重要。 因为这是第一次发现：「Minecraft内部 存在接近纯函数的领域。」
Pure Compute
此时尚未形成正式术语。 但后来逐渐演化为：
Definition-001
Pure Compute Domain
满足：
输入固定

↓

结果固定

↓

不修改真实状态
例如：「AE2 Craft Planner」
不满足：「Hopper Redstone Entity Tick World Tick」
这成为后续全部理论的基础。
一个危险误区
在此时期。 产生了一个非常自然的联想。
如果：「AE2 Craft Planner」成功。
那么是否说明：「所有 BlockEntity 都能这样处理？」
这是后来被证明最危险的推论之一。
Failed Route-002
Universal VM
假设：
所有BE

↓

ByteCode

↓

VM

↓

Worker
这种路线后来被基本否定。
原因非常简单。
AE2：「规划 只是规划」
不修改世界。
而：「漏斗」必须：「读取容器 修改容器」
「红石」必须：「传播状态 改变邻居状态」
「Create动力系统」必须：「传播应力 修改网络状态」
这些系统：「副作用」无法忽略。
于是出现一个全新的判断标准。
Discovery-002
问题不在于：「它是不是BlockEntity」
而在于：「它有没有副作用」
这个发现改变了整条研究路线。
以前判断标准：「计算量」
后来判断标准：「副作用」
最终形成：
Rule-002
副作用比计算量更重要。
Snapshot 的出现
随着 AE2-VM 思路深化。 出现另一个概念。
如果：「Worker 不能访问真实世界」
那么：「Worker 看什么？」
答案：「Snapshot」
于是形成：
Live State

↓

Snapshot

↓

Worker

↓

Result
模式。
第一次明确出现。
Definition-002
Snapshot Isolation
工作线程：「只读取快照」
主线程：「维护真实状态」
两者隔离。
不竞争。
不加锁。
尽可能不共享。
后来这成为：「Snapshot Runtime」理论基础。
Worker 真的安全吗？
很快。 讨论进入更深入层面。
发现一种情况。
工作线程看起来：「只是读」
实际上：「getSomething()」内部可能：「rebuildCache() updateInternalState()」
即：「看起来在读 实际上在写」
这是 Minecraft Mod 中极为常见的问题。
后来形成：
Constraint-001
Hidden Side Effect
隐藏副作用。
判断纯函数时。 不能相信：「getter」名字。
必须相信：「源码行为。」
这是后来所有 Snapshot 理论都必须面对的问题。
AE2-VM 的真正价值
经过分析。 研究逐渐收敛。
AE2-VM 成功。 并不是因为：「VM」
也不是因为：「JIT」
真正原因是：「快照 纯函数 无副作用」同时成立。
于是形成：
ADR-002
AE2-VM 是领域成功案例。 不是通用引擎。
这句话后来影响极大。
因为它明确指出：「成功案例 ≠ 普适规律」
本章最终结论
研究方向发生第二次重要转折。
研究对象： 从「JIT」变成：「Snapshot」
从：「VM」变成：「Pure Compute Domain」
从：「优化所有东西」变成：「寻找可优化的东西」
Rule-003
不要问：「如何并行化Minecraft？」先问：「Minecraft哪些部分 本来就适合并行化？」
引向下一章
此时新的问题出现。 如果：「副作用」是真正边界。 那么：「Minecraft中 到底有哪些副作用？」

Chapter 3
副作用、状态与 Minecraft 的第一定律
新问题
AE2-VM 的研究带来了一个新发现：「不是因为VM成功 而是因为Craft Planner是纯函数」
于是新的问题出现了：「什么叫副作用？」
以及：「副作用为什么会毁掉并行化？」
在大多数软件工程领域。 副作用只是一个语言概念。
而在 Minecraft 中。 副作用几乎决定了：「一切。」
状态的发现
此阶段的讨论开始从：「线程」转向：「状态」
最初很多优化思路都隐含一个假设：「计算很贵」
后来逐渐发现：「计算未必贵。」
真正昂贵的是：「状态同步。」
例如：
int result =
    planner.plan(item);
如果：「planner」只依赖：「Snapshot」
那么：「多少线程都好办。」
问题在于：
world.setBlock(...)
或者：
inventory.extract(...)
或者：
entity.move(...)
此时：「世界状态发生变化。」
变化意味着：「别的系统可能受到影响。」
而这正是 Minecraft 的核心。
Minecraft不是模拟器
此时产生一个重要观点。
许多程序：
输入

↓

处理

↓

输出
例如：「图片压缩 视频编码 数学计算」
这些系统天然适合：「多线程」
Minecraft 不一样。
Minecraft 本质上更像：「巨大的状态机。」
任何时刻。 世界由：「Block State Entity State NBT State Player State Chunk State」共同构成。
计算本身并不是重点。
重点是：「谁有权修改状态？」
于是逐渐形成一个后来非常重要的概念。
Definition-003
State Ownership
状态所有权。
任何状态。 必须回答：「属于谁？」
例如：「这个库存 属于谁？」
「这个实体 属于谁？」
「这个Chunk 属于谁？」
如果：「多个线程同时拥有」
最终往往变成：「锁」
或者：「崩溃」
或者：「幽灵BUG」
幽灵BUG
随着讨论深入。 开始意识到：「崩溃不是最可怕的。」
最可怕的是：「偶尔出错。」
例如：「服务器运行100小时 正常」
「第101小时 丢了一组钻石」
之后：「永远无法复现。」
这类问题后来被归类为：
Constraint-002
Heisenbug
观察不到的并发错误。
在 Minecraft Mod 环境中。 这类问题尤其严重。
因为：「几千个Mod 默认都相信： Minecraft只有一个主线程。」
第一次定律
经过大量讨论。 研究开始收敛。
最初认为：「多线程问题 是性能问题。」
后来发现：「多线程问题 其实是状态问题。」
于是得到全书第一个真正意义上的定律。
Law-001
Minecraft 第一状态定律
首先取决于它对状态的控制能力， 而不是它的计算复杂度。
举例：
AE2 Craft Planner「计算量高 状态修改低」
结果：「容易并行。」
红石系统「计算量不高 状态传播极强」
结果：「极难并行。」
漏斗系统「计算量低 状态交互极高」
结果：「极难并行。」
Create 动力网络「计算量中等 状态传播极高」
结果：「需要非常谨慎。」
线程神话的破灭
此时研究发生第三次转折。
最初目标：「线程化Minecraft」
随后目标：「线程化AE2」
此时开始变成：「识别状态边界。」
因为：「线程池 Worker VM JIT」都属于：「工具。」
而：「状态边界」才是：「规则。」
第一次形成：
Rule-004
不要先讨论：「线程。」先讨论：「状态。」
状态分类学（雏形）
此时开始出现第一个分类系统。
Class A
Pure State 特点：「可复制 可快照 无副作用」
例：「Craft Planner Snapshot」
Class B
Derived State 特点：「可重新计算」
例：「缓存 索引 路径结果」
Class C
Authority State 特点：「真实状态 必须唯一」
例：「Inventory Chunk World」
Class D
Temporal State 特点：「依赖顺序」
例：「红石 Tick链 实体更新」
未来的大部分理论。 都会建立在这个分类之上。
本章结论
研究方向再次收缩。
从：「如何并行？」变成：「什么状态允许并行？」
最终形成：
ADR-003
线程问题只是状态问题的表现。
ADR-004
副作用本质上是：「状态传播。」
Chapter Summary
本章结束时。 研究者终于不再把：「Minecraft 看作： 一个程序」
而开始把它看作：「一个巨大的状态系统。」

Chapter 4
Amdahl 定律：为什么线程分离不一定带来收益
新阶段
到目前为止。 研究已经经历三次转折。
第一次：「JIT幻想」
第二次：「Pure Compute Discovery」
第三次：「状态优先」
此时。 研究者已经不再争论：「Minecraft能不能多线程？」
而开始讨论：「即使多线程成功 收益会有多大？」
这是第四次重要思想转折。
一个危险错觉
几乎所有刚接触并行计算的人。 都会产生一个天然想法。
例如：「CPU: 16核心」
然后认为：
我让Minecraft吃满16核

↓

性能提升16倍
这非常符合直觉。
也几乎总是错误的。
Amdahl 定律登场
在并行计算领域。 存在一个著名公式。
Amdahl's Law
定义：
Speedup

=

1

/

(

(1-P)

+

P/N

)
其中：「P」表示：「可以并行化部分」
而：「1-P」表示：「必须串行执行部分」
第一个例子
假设：「Minecraft Tick 20ms」组成：「18ms 串行 2ms 可并行」
即：
P = 10%
即使拥有：「无限CPU核心」
理论极限：
20ms

↓

18ms
提升：「1.11x」
不是：「16x」
甚至不是：「2x」
于是出现一个残酷现实：
Discovery-003
能并行 不代表值得并行。
桃路线的修正
此时期。 讨论中出现重要修正。
前期观点：「线程剥离 是多核优化基础」
后期观点：「线程剥离必须建立在热点之上」
这个区别极大。
错误顺序：
线程池

↓

调度器

↓

VM

↓

寻找工作
正确顺序：
Profiler

↓

热点分析

↓

发现纯计算

↓

快照化

↓

线程剥离
后来形成：
Rule-005
不要先设计线程。 先设计工作。
AE2 为什么重要
此时。 AE2 开始被重新理解。
AE2 最大价值并不是：「它快」
而是：「它提供一个容易隔离的负载样本」
例如：「Craft Planner」属于：「高计算量 低副作用」
这是理想目标。
这种系统即使只占：「主线程30%」
也值得投入大量研究。
因为：「30%」已经足以产生明显收益。
Minecraft 的残酷现实
此时出现另一条讨论线。
观察：「Minecraft 很多系统并不复杂。」
复杂的其实是：「状态同步」
例如：「Hopper」
逻辑非常简单：「取物品 放物品」
计算复杂度极低。
问题在于：「库存被改了」
库存一变。
可能影响：「漏斗 管道 AE网络 机器 玩家」
于是：「状态传播」远比：「计算」昂贵。
第一次负优化理论
此时出现一个重要概念。
Definition-004
Negative Parallelism
负并行化。
即：「线程创建 调度 同步 回传」成本。
大于：「实际计算成本。」
例如：「计算 10μs」
线程调度：「100μs」
结果：「更慢。」
这在 Minecraft 中极其常见。
因此：
Rule-006
线程必须足够粗。
任务粒度太小时。
线程池本身变成性能瓶颈。
DAG 的出现
讨论此时开始接触：「Task Graph」思想。
观察： 许多 BlockEntity。
修改范围有限。
例如：「机器A 只影响机器B」
于是：
A

↓

B

↓
