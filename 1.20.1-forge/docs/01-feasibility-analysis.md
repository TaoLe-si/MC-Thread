# MC Thread 可行性分析

> 版本：v0.1（框架阶段）
> 依据：《Minecraft Runtime Research Notes》（Draft 0.1，见 [摘要](reference/research-notes-summary.md) 与全文 `reference/research-notes-full.txt`）

## 1. 项目定位

MC Thread 是一个运行在 **NeoForge 1.20.1（Forge 兼容）** 上的运行时层模组。它的目标不是"优化某一个模组"，而是：

1. 为所有模组提供一套**度量体系**（Profiler / Replay / Benchmark），先回答"时间到底花在哪"；
2. 提供一套**计算与交互分离的运行时 API**（快照 → 工作线程 → 校验 → 主线程提交），让模组作者可以选择性地把高计算、低副作用的工作移出主线程；
3. 对生态**通用热路径**做低层优化（不要求目标模组适配）；
4. 预留可选的 **Domain Adapter** 扩展点（不绑定特定模组；核心路线是通用运行时优化）。

最终可感知的成果：在模组负载较重的服务器上，把主线程 Tick 耗时降下来，恢复或稳定 20 TPS。

## 2. 从研究笔记继承的核心结论

笔记从"JIT 幻想"一路收敛到"Runtime 家族"，其结论对本项目几乎全部适用，直接采纳如下：

| 编号 | 结论 | 对本项目的影响 |
| --- | --- | --- |
| Law-001 | 状态控制能力决定可并行性 | 先识别"高计算、低副作用"的领域，而不是先开线程 |
| Law-002 | 无法测量的问题无法正确优化 | **M1 必须先是 Profiler/Replay/Benchmark** |
| Law-003 | 不能快照的系统无法安全并行 | 所有 offload 任务必须建立在快照之上 |
| Law-004 | 正确性优先于性能 | 校验（Validation）不可省略；实验特性默认关闭 |
| Law-005 | 不能表达变化的事务难以安全并行 | 只对"变化可表达"的系统做事务化 |
| Law-006 | 只有适用于特定领域的优化模型 | 拒绝"万能 VM"，走 Domain Adapter |
| Law-007 | 共享状态最终会回到锁 | 用所有权/消息传递消灭共享写，而不是加锁 |
| ADR-007/008/009 | Profiler 先于线程；Replay 先于 Runtime；Benchmark 先于优化 | 开发顺序强制为度量先行 |
| ADR-017/018/019 | Snapshot 先于 Worker；Validation 不可省略；Live State 属于主线程 | 运行时 API 的核心纪律 |
| ADR-032 | Adapter 优先于 Universal VM | 通用能力有限，领域适配是现实路线 |
| Failed Route-001 | 缓存 READ 结果不可作为通用方案 | 缓存必须基于"变化传播"而非"结果缓存" |
| Failed Route-002 | 万能 VM 被否定 | 不做"所有 BlockEntity 统一 VM" |

笔记给出了一份**领域评分表**，是本项目选择优化目标的重要依据：

| 领域 | 评分 | 说明 |
| --- | --- | --- |
| Craft Planning（合成规划） | ★★★★★ | 纯计算、无副作用、输入稳定 |
| Inventory Simulation（库存模拟） | ★★★★★ | 事务模拟、可回滚 |
| Storage Query（存储查询） | ★★★★☆ | 读多写少，适合快照 |
| Path Search（路径规划） | ★★★★☆ | 图搜索、副作用低 |
| Entity AI | ★★★☆☆ | 半状态半计算，需细分 |
| Redstone / Hopper | ★☆☆☆☆ | 时序敏感、强传播，**早期禁止** |

## 3. 技术前提：1.20.1 NeoForge 的现实约束

### 3.1 线程模型

- 专用服务器上，**世界状态只允许 Server Thread 修改**。NeoForge 的事件总线（`MinecraftForge.EVENT_BUS`、Mod 事件总线）都在主线程分发。
- 任何模组把"修改世界"的工作放到别的线程，除非通过游戏自己提供的异步机制，否则就是非法访问。
- 因此"把交互线程统一到同一线程"这个直觉，在 1.20.1 上的**正确含义是**：
  - 主线程是唯一的"交互线程"（Live State 的所有者）；
  - 我们能做的，是把**可延后/可批处理/纯计算**的工作从主线程移走，再以受控方式交回主线程提交。
- **Folia 是 Paper（Bukkit）生态**，与 NeoForge 完全不兼容；"区域所有权"路线在本项目只能借鉴思想（所有权、消息传递），不能照搬。

### 3.2 生态热路径

模组数量一多，以下通用路径会显著吃主线程时间：

- **事件分发**：高频率 Tick 事件（`ServerTickEvent`、`LevelTickEvent`、实体/方块实体 Tick 事件）的监听器遍历与调用；
- **能力（Capability）查询**：`BlockEntity#getCapability` 是链式 Provider 查找，大型科技基地每秒可能触发数百万次，且伴随大量临时对象分配；
- **方块实体/实体 Tick**：每个 BE 的 `tick()` 在主线程顺序执行，模组间没有隔离；
- **NBT 序列化 / 存档写入**：保存阶段在主线程或受限线程执行；
- **网络包序列化与分发**：高频小包在主线程处理；
- **GC 压力**：热路径上无谓的流式分配、临时 `Optional`/`ItemStack` 包装。

### 3.3 Amdahl 上限（先泼冷水）

Tick 预算 50ms（20 TPS）。假设 Profiler 证实"纯计算热点"占 30%：

```text
理论加速上限 = 1 / (0.7 + 0.3/N) ≈ 1.43x（N→∞）
```

这意味着：

- 即使无限核，最多也只挽回约 14ms 的 tick；
- 对"TPS 从 12 恢复到 20"这种目标，真正有价值的是**先量化**：到底是 30% 纯计算热点，还是 70% 都在锁竞争/状态同步/序列化上；
- 项目验收必须以"恢复到 20 TPS 的占比"为指标，而不是"吃了多少核"。

## 4. 候选方案严格分析

### 方案 A：交互线程统一化（原始设想）

**原理**：把所有模组-游戏交互任务集中到一条"交互线程"顺序执行，避免多线程锁竞争。

**收益模型**：消除锁竞争、减少上下文切换、提升缓存局部性。

**严格分析**：

- 主线程本身就是唯一的交互线程。把交互任务搬到另一条线程，并不会减少主线程的工作量；
- 若该线程与主线程共享世界状态，那么同步成本 ≥ 原成本（Law-007：共享状态最终回到锁）；
- 该方案**只在"交互"是可延后提交的工作（异步 IO、序列化、批量网络、保存）时成立**。

**结论**：采纳其内核，但收缩范围——运行时提供一条**单一交互执行器**（`InteractionExecutor`），只处理"可延后、可批处理、不即时影响 Tick 结果"的任务；即时世界修改仍然必须回到主线程。

### 方案 B：Snapshot / Worker / Validation（研究主线）

**原理**：主线程构建只读快照 → 计算线程池执行 → 提交前校验 → 主线程提交。

**收益模型**：把高计算低副作用的域（Craft Planning / Path / Storage Query）移出主线程；收益 = 热点比例 × 纯计算比例 × 快照可行性（ADR-006）。

**成本**：快照构建、校验本身有主线程开销（Constraint-005）；隐藏副作用可能让 getter 变成写操作（Constraint-001）。

**结论**：这是**核心路线**，但只能作用于"主动适配 API 的模组"，无法强制第三方模组。

### 方案 C：Delta 增量传播

**原理**：只传播变化，避免全量重扫；最好计算是不发生的计算（Rule-010）。

**约束**：需要目标系统提供可观测的变化源（库存版本、网络拓扑版本）。笔记将其列为 Strong Hypothesis：大型科技网络中"变化量远小于状态量"。

**结论**：作为运行时内部的缓存失效/脏标记机制使用，而不是对第三方模组的通用手段。

### 方案 D：Folia 式区域所有权

**结论**：**不可行**（平台不兼容）。仅借鉴"所有权 + 消息传递"思想，用于运行时 API 的线程纪律设计。

### 方案 E：通用 Mixin 低层优化

**原理**：在生态通用热路径注入优化，例如：

- 能力查询快速路径（缓存 + 快速失败）；
- 高频事件分发归因与减支；
- 热循环分配减少（复用缓冲区、避免流式分配）。

**优势**：对所有模组生效，不需要目标模组适配。

**风险**：Mixin 冲突、行为差异（Heisenbug，Constraint-002）、版本脆弱。

**结论**：可行，但**每一项必须 A/B Benchmark 验证、独立开关、默认关闭或保守开启**（Rule-008 / ADR-009）。

## 5. 底层优化清单（按分类学评分）

> 评分维度：影响面（多少模组受益）、复杂度、风险、预期收益。证据要求指"证明它值得做"需要什么。

| # | 优化项 | 机制 | 影响面 | 复杂度 | 风险 | 预期收益 | 证据要求 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 1 | 能力查询快速路径 | 缓存 Capability Provider 链 + 无能力快速失败 | 所有模组的 BE/实体交互 | 中 | 中 | 高 | 分配热图 + 基准 |
| 2 | Tick 归因 Profiler | 事件/监听器/BE 类型级采样归因 | 全生态（度量） | 低 | 低 | 间接（决策依据） | 可重复输出 |

| 8 | 红石/漏斗优化 | - | 全生态 | 极高 | 极高 | 低 | 笔记明确否决（★1） |

## 6. 如何提高通用性

1. **API 与实现分离**：`mcthread.api` 包只依赖 Minecraft/NeoForge 公共 API，发布独立 dev artifact（`./repo` 或 Maven），第三方模组编译期即可接入；
2. **无硬依赖**：不绑定任何目标模组；全部为可选运行时检测，缺省不加载 Adapter；
3. **配置驱动**：每个特性独立开关，支持按服务器/客户端预设；
4. **最小注入面**：Mixin 只打在少量、可枚举的注入点，优先级低、失败可降级，避免与生态冲突；
5. **平台兼容**：NeoForge 1.20.1 为 Forge 兼容线（官方 MDK 使用 `net.minecraftforge:forge:1.20.1-47.1.3` 构件，以 `forge` 为 loader id），一份 jar 可同时覆盖 Forge 47.1.3+ 与 NeoForge 47.1.x（至 47.1.106）两个生态；
6. **适配器模式**：`Domain Adapter` 接口公开，社区可为其模组贡献适配器，不依赖本模组核心改动。

## 7. 风险与对策

| 风险 | 等级 | 对策 |
| --- | --- | --- |
| Heisenbug / 幽灵 BUG | 高 | 确定性 Replay 复现、Validation 强制、实验特性默认关闭、长时间 soak 测试 |
| Mixin 冲突 | 中 | 注入点最小化、可开关、失败降级、冲突报告 |
| 收益不足（负优化） | 中 | Rule-006 任务粒度约束；每项优化 A/B 基准 ≥5% 才保留 |
| 第三方模组拒绝适配 | 中 | 通用热路径优化不要求适配；Adapter 模式降低接入门槛 |
| Folia 类多线程被误期待 | 中 | 文档明确边界：本模组不做区域线程化 |
| 快照过期 | 高 | 乐观并发 + 版本校验 + 重试（Transaction Runtime 基础） |

## 9. 结论

**可行，但必须以"度量驱动 + 运行时服务 + 通用低层优化"为核心、Domain Adapter 为可选扩展的组合落地**，而不是"把所有模组交互搬到一条线程"这种单一动作。研究笔记的九次转向指向同一个答案：**先解决状态问题，再解决线程问题；先测量，再优化。**

第一阶段（M1）的成果不是"优化"，而是"看得见优化"的能力——这本身就是最有通用性的交付物。

方案 A 已用最小 spike 回访，见 [交互卸载实验](05-interaction-offload-experiment.md)：可行的是「快照请求 → 交互线程判定 → 主线程写回」，不是把原版 `useOn` 整段搬出主线程。
